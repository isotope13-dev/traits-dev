# Fragmented WSH and Python review

Forty-six rules moved out of the fragmented and Python-script dropper leaves.
Individual short fragments are components and describe their literal text;
fragment combinations are evidence profiles until the required operations
support a probable download-and-launch chain. Those chains use the network
file-execution sink.

Pip/EXE name proximity, an escaped byte sequence, and TEMP/EXE text no longer
claim that a file was staged or opened. An embedded PE literal plus a TEMP
reference and shell call does not require a write; an encoded-looking literal
plus shell and remove calls does not require decoding. Those combinations are
suspicious profiles. RC4, zlib and a four-byte marker do not by themselves
establish a beacon, and WinPython, pythonw and a Run-key reference do not
establish a registry write. The stronger manifest, archive and decoded-carrier
execution combinations retain their execution homes.

The hosts-file dropper ancestor consumer retains the moved alternatives. Its
existing URL-construction, executable-config and process-artifact selectors
already cover the relevant moved observations. The plugin consumer's prior
URL-construction directory selector was replaced by its eight then-current
members before the counter-fragment profile moved there, preventing a weak
new URL clue from widening that consumer.

The single-fragment leaf was approaching its limit. Seven existing fragments
containing source syntax moved to the syntax-fragment sibling; seven new
syntax-bearing fragments and twelve individual literal fragments were placed
accordingly. The 78-rule Run-key leaf was reduced by moving twelve
script-oriented registry-registration rules to the existing registry-script
category. Two former whole-Run-key consumers retain those twelve exact
alternatives. Descriptions now identify HTTP context without asserting that a
request timeout alone establishes periodic beaconing.
