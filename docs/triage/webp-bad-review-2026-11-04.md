## Completed legacy-length investigation

Completed direct review of the remaining `8a09008acddb` image's container and frame data, including decoder versions 0.6.1, 1.2.0 and 1.2.1. The ordinary whole-file decoder rejects a RIFF or VP8 payload length exceeding available bytes when `have_all_data` is set. The older demuxer's StoreFrame clamps payload availability to the available buffer and returns NEED_MORE_DATA for the declared excess. This sample has a simple VP8 chunk and does not enter the optional-chunk path associated with the investigated legacy chunk-size reports. Normalizing only the two length fields in an analysis copy permits complete current-library decoding and visual inspection of a gray, blocky 1,056×576 frame. The original bytes were preserved; the normalized copy is not classified in their place. Sources and analysis copy are under `/var/tmp/webp-legacy-review/`; [the upstream decoder source](https://chromium.googlesource.com/webm/libwebp/+/refs/tags/v0.6.1/src/dec/webp_dec.c) supports the described guards.

Disposition: **inconclusive**. Substantive review is complete, but I cannot establish whether these synchronized 0x2020 length mutations implement an exploit primitive against some other decoder or are merely corrupt/fuzzed image data. The available container/frame analysis and reviewed implementations establish neither a benign original nor a known executable exploit. This is a specific interpretation/decoder-coverage limit, not unknown operator authorization or a substitute for the completed parsing investigation. Retain the accurate structural-problem observation and exclude this exact artifact from binary training; do not invent a hostile rule for oversized lengths alone.
